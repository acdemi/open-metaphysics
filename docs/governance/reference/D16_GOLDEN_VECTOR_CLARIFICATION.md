## 3. Evidence

### 3.1 「golden vector」的结构在规范中有**冻结定义**

`docs/specification/IMPLEMENTATION_GUIDE.md` **§5 Golden Vector Format**（L157-184）——逐字：

```text
Each golden vector is a JSON object:

    {
      "vector_id": "gv:rule:4ac4eda17425",
      "layer": "rule",
      "name": "01_single_condition",
      "description": "",
      "input": {
        "rule_yaml": "...",
        "chart_data": { ... }
      },
      "expected_output": [ ... ]
    }

The `expected_output` field type varies by layer:
| rule | list (RuleEvaluation[]) |  | pattern | dict (PatternMatch) or null |
| evidence | list (Evidence[]) |  | knowledge | dict (KnowledgeResult) |
| consensus | dict (ConsensusReport) |

Golden vectors are stored per-layer in
`reference/conformance/golden/{layer}_vectors.json`.
```

同一结构在 Reference 实现中以冻结模型固化：`reference/conformance.py:44-51`
`class GoldenVector`（字段 `vector_id` / `layer` / `name` / `description` / `input` / `expected_output`，
且 `extra="forbid"`，见 `:45`）。

### 3.2 RuntimeAdapter 协议只有 6 个方法，**没有**行为验证面

`reference/conformance.py:99-110` `class RuntimeAdapter(Protocol)`：
`evaluate_rule` / `match_pattern` / `match_pattern_cross_system` / `build_evidence` /
`query_knowledge` / `build_consensus`。

**推论**：CF-018 要求 `expected_output` 为「adapter **produces** 的精确 canonical JSON」，
但 adapter **无法**按行为合约 ID 产出输出 —— 因此「为每个行为合约造一条传统向量」
在现有协议下**没有直接的 input → expected_output 语义**（详见 §6 Option B 约束）。

### 3.3 CF-015 未自行定义结构，依赖同集合其他条款

CF-015（§1.1）只写 "golden vector"；其结构由 **IMPLEMENTATION_GUIDE §5**（§3.1）、
**CF-017**（存放位置与文件数）、**CF-018**（`expected_output` 语义）、**CF-019**（层集合）共同确定。
→ 在同一规范集合内，该术语**有确定指称**，不能被任意解释为「任何可执行检查」。

### 3.4 全库检索：**无任何条款**允许以非 vector 形式替代

- `docs/specification/*.md` 中 `golden vector` / `GoldenVector` 的全部出现点均在
  `CONFORMANCE_SPEC.md` 与 `IMPLEMENTATION_GUIDE.md`（见 `§3.1`、`§1.2`），**没有任何一条**
  授权以「可执行验证器 / behavior representation」替代 golden vector。
- 相反，**CF-016**（L280-291）规定 Conformance **MUST NOT** 修改或重定义 Behavior Contract，
  也不得新增行为规则 —— 未授予形态裁量。

### 3.5 P1-1 新增的 ConformanceResult 字段未见于 §5 字段表

`CONFORMANCE_SPEC.md` §5（L356-367）的 `ConformanceResult` 字段表**不含**
`behavior_coverage` / `unrepresented_behaviors`（P1-1 新增，`reference/conformance.py:81-82`）。
该表并未声明自身穷尽；**CF-014**（L252-263）只强制 `contract_version` 与 `behavior_version` 必须上报（已满足）。
→ 这是**第二个、较小的字面对齐问题**，与 CF-015 同类，一并披露供裁定。

### 3.6 `certify()` 已把行为 ID 汇入 Manifest

`reference/conformance_runner.py:707+`：`ConformanceManifest.supported_behaviors` 取自
`category == BEHAVIOR_COVERAGE and passed` 的 check `name` → 现为 **52 个 ID**。
`CONFORMANCE_SPEC.md` §6（L371-384）确有 `supported_behaviors`（"Behavior contract IDs covered"）字段，
但 **CF-015 的规范措辞**是 "represented by at least one **golden vector**"，
**不是** "listed in the manifest" —— 不能以此替代 CF-015 的字面要求。

## 4. Literal Compliance Analysis

### 4.1 Task 1 四问的逐条回答

**Q1：CF-015 是否明确要求 "vector" 必须具有固定的数据结构？**

- **CF-015 本条：否** —— 该条只使用术语，不定义结构（`CONFORMANCE_SPEC.md` L265-278）。
- **同一规范集合整体：是（间接但确定）** —— 结构由 `IMPLEMENTATION_GUIDE.md` §5（L157-184）
  给出七字段 JSON 形态与逐层 `expected_output` 类型，并由 `reference/conformance.py:44-51`
  的 `GoldenVector` 冻结模型与 `extra="forbid"` 固化；位置/文件数由 CF-017（L293-305）确定，
  `expected_output` 语义由 CF-018（L307-319）确定。

**Q2：是否存在对 golden vector schema 的冻结定义？**

- **存在**。三处互相印证：① `IMPLEMENTATION_GUIDE.md` §5（L157-184）格式与逐层类型；
  ② `reference/conformance.py:44-51` 的 `GoldenVector`（`extra="forbid"`，字段固定）；
  ③ CF-017（存放于 `reference/conformance/golden/{layer}_vectors.json`、文件数 **MUST** = 5）
  与 CF-019（层枚举恰为 5 个）。

**Q3：当前 executable verifier 是否已被其他规范明确允许作为 golden vector 的替代形式？**

- **否**。全 `docs/specification/` 检索（§3.4）**没有任何条款**作此授权；
  CF-016 甚至禁止 Conformance 重定义行为合约。当前的替代属于**实现自决**，
  而非规范授权。

**Q4：P1-1 是否可以在不修改任何规范文字的情况下声称满足 CF-015？**

- **按字面口径：不能。** 理由链：
  1. CF-015 要求每个行为合约「represented by at least one **golden vector**」（L274-275）；
  2. 同集合已把 "golden vector" 固定为「`{layer}_vectors.json` 中的七字段 JSON 对象」（§3.1、§3.3）；
  3. P1-1 的代表物是 **Python callable**，既不在那 5 个文件中，也非 `generate_golden_vectors()` 产物；
  4. 无任何条款授权替代（Q3）；
  → 因此 P1-1 的机制在**实质强度上不低于甚至高于** CF-015 的意图（执行真实断言而非快照比对），
  但在**字面一致性上未成立**。

- **可成立的部分**：CF-015 的另两句已被完全满足 —— 「verifies a known set」已从 17 扩到 **52**（`conformance_runner.py:37`），
  「Missing coverage MUST fail」已实现（无代表物 → `passed=False`，`:636-682`）。
  **唯一未闭合的是「represented by … golden vector」这一句的形态要求。**

### 4.2 结论（不改规范即不能宣称字面合规）

```text
CF-015 字面一致性：NOT ESTABLISHED（P1-1 现状）
CF-015 覆盖语义  ：SATISFIED（52/52 已执行、缺失即失败）
```

## 5. Option A

**定义（按任务书）**：把当前 executable behavior verifier **正式解释为**
`golden behavior representation`，并确认其满足 CF-015 的**规范意图**。

**规范依据评估**

- 支持「意图已满足」的事实：CF-015 的三句话中，「known set」「missing → fail」两句已达标；
  行为被真实执行、可追溯、且比快照更严格。
- **但**要把 executable verifier 认定为 CF-015 意义上的代表物，必须处理 §3.1/§3.3 已固定的术语：
  `IMPLEMENTATION_GUIDE.md` §5 与 CF-017/CF-018 把 golden vector 绑定到
  「`{layer}_vectors.json` 中的对象 + adapter 产出 expected_output」。
  → **Option A 并非"零规范改动"**：它要么（A1）**修订 CF-015 措辞**（例如显式允许
  "executable behavior representation" 等价物），要么（A2）由人工出具一份**解释性裁定**，
  认定现有文本已涵盖该形态。
  - A2 的风险：与 CF-017/CF-018 的字面并存解释困难（callable 不在那 5 个文件内、
    非 `generate_golden_vectors()` 产物），且 CF-016 明确禁止 Conformance 自行重定义行为合约。
  - 因此 A1（改规范文字）在规范上更自洽；A2 只在「明确承认其为有意的解释性偏离并留档」时成立。

**对现有实现的影响**：无（P1-1 保持不变）。

## 6. Option B

**定义（按任务书）**：严格按 CF-015 字面，为 52 个行为各补一条
`input → expected output` 的机器可执行 golden vector。

**现行规范施加的硬约束（这些约束决定 B 不是"加 52 条 JSON"那么简单）**

| 约束 | 出处 | 对 Option B 的含义 |
|------|------|-------------------|
| 向量 **MUST** 由 `generate_golden_vectors()` 自动生成；手工编辑 golden 文件属**违规** | CF-013（L238-250） | 必须**扩展生成器**，不能手写向量 |
| 向量 **MUST** 自动发现，且**文件数 MUST = 5** | CF-017（L293-305） | **不得新增 `*_vectors.json` 文件**；新向量只能落入现有 5 个文件 |
| `expected_output` **MUST** 为 adapter **产出的**精确 canonical JSON | CF-018（L307-319） | 需要为"行为向量"定义 adapter 侧产出语义 |
| 五层各 ≥1 向量 | CF-019（L321-333） | KB/CS 行为应归入 KNOWLEDGE / CONSENSUS 层；BC 归 RULE/PATTERN/EVIDENCE |
| Conformance **MUST NOT** 重定义行为合约 | CF-016（L280-291） | 不得把行为语义搬进 conformance |
| adapter 协议恰为 6 方法，无行为验证面 | `reference/conformance.py:99-110`（§3.2） | **CF-018 的 expected_output 无法对行为 ID 成立** → B 需要先裁定"行为向量的 input/expected_output 是什么"，可能需扩展 `RuntimeAdapter` 协议（另一冻结工件） |

**可选实现变体（仅作为决策输入列出，不预选）**

- **B-1**：扩展生成器，为每个行为 ID 生成一条向量，其 `input` 为行为探针参数、
  `expected_output` 为**adapter 在该参数下产出的 JSON**。需要先解决「adapter 如何按行为 ID 产出」。
- **B-2**：给现有/新增向量增加 **`behavior_ids` 标注**，建立「ID ↔ 向量」的机器可读映射，
  再由 CF-015 检查按该映射核对。此变体不新增真实 diff 语义，但**能满足"represented by at least
  one golden vector"的字面**；同时它**仍会改动** `generate_golden_vectors()` 与 5 个向量文件
  （CF-013/CF-018 的再生一致性必须继续成立）。

**对现有实现的影响**：`_behavior_representation()` 与 `_check_behavior_coverage()` 需改为
以「向量映射」为主判据（否则会与 B 的字面口径不一致）；`GoldenVector` 模型可能需扩展字段。
